# Page 09 — Warehouse & Inventory Management

## Overview

Page 09 adds a Hub In-Charge-only warehouse and inventory workspace at `/app/warehouses` and warehouse details at `/app/warehouses/:id`. It is incremental and preserves the Node.js native HTTP server, SQLite (`node:sqlite`), vanilla JavaScript, existing HTML/CSS and Chart.js.

## Actual database relationships

- A hub is a `warehouses` row. No separate hub table is introduced.
- `inventories.warehouse_id` references `warehouses.id`.
- Inventory records carry `sku`, `item_name`, `quantity`, `reserved_quantity`, `reorder_point`, `unit_cost` and `updated_at`.
- When the optional `products` table exists (such as after the expanded workbook import), `inventories.sku` joins to `products.sku`. If the table is absent, the API falls back to inventory's stored item name/category and product-wide inventory lookup reports `available: false` rather than inventing a product.
- `shipments.origin_warehouse_id` and `shipments.destination_warehouse_id` reference warehouses. A shipment matching both sides is returned once.
- `shipment_items.shipment_id` references shipments; `shipment_items.sku` can be matched to inventory SKU to identify item-level overlap. An affected inventory record is counted only where an active/investigating disruption is attached to that shipment and the inventory warehouse is its origin or destination.
- `disruptions.warehouse_id` is a direct warehouse relationship. Disruptions attached to a shipment are also associated with its verified origin/destination warehouses. Inventory-source disruptions are associated only when their source record maps to an inventory record in that warehouse. Unassigned disruptions are not allocated.
- `customer_orders.assigned_warehouse_id` references warehouses. Additional affected orders are included only through `disruption_affected_orders` and the verified disruption/warehouse/shipment chain.
- `recovery_plans.disruption_id` references disruptions; `recovery_actions.recovery_plan_id` references recovery plans. Recovery plans are shown only when their disruption is linked to the warehouse through one of the verified relationships above.
- `audit_logs` is the activity source. No activity records are generated by this read-only module.

## Inventory calculations and classification

`available_quantity = MAX(0, quantity - reserved_quantity)`.

- **Out of Stock:** available quantity equals zero.
- **Low Stock:** available quantity is greater than zero and less than or equal to the stored `reorder_point`.
- **In Stock:** available quantity is greater than the stored `reorder_point`.

This is a derived classification, not a stored status. The module does not alter inventory quantities, reserved quantities, reorder points or source provenance. A physical unit total is presented separately from inventory record count. No arbitrary low-stock threshold is introduced.

## Backend service

`src/services/inventory-service.js` implements:

- Overview metrics and stock distribution.
- Warehouse register search, status/location/disruption filters, pagination and stable sorting.
- Warehouse identity and operational summary.
- Warehouse inventory, shipment, disruption, affected-order, recovery and activity collections.
- Global inventory register, inventory record detail and optional product-level inventory lookup.

All user-supplied values are bound parameters. Sort columns are selected from an allowlist. Warehouse and inventory endpoints are protected in `server.js` using the existing `HUB_INCHARGE` role guard. There are no write endpoints for stock adjustments or transfers.

## API endpoints

- `GET /api/v1/inventory/overview`
- `GET /api/v1/warehouses?page=&limit=&q=&status=&location=&disruption=&sort=&direction=`
- `GET /api/v1/warehouses/:id`
- `GET /api/v1/warehouses/:id/inventory?page=&limit=&q=&status=&product=`
- `GET /api/v1/warehouses/:id/shipments?page=&limit=&q=`
- `GET /api/v1/warehouses/:id/disruptions?page=&limit=&q=`
- `GET /api/v1/warehouses/:id/orders?page=&limit=&q=`
- `GET /api/v1/warehouses/:id/recovery?page=&limit=&q=`
- `GET /api/v1/warehouses/:id/activities?page=&limit=&q=`
- `GET /api/v1/inventory?page=&limit=&q=&status=`
- `GET /api/v1/inventory/:id`
- `GET /api/v1/products/:id/inventory` (only available when a products table and matching product record exist)

Pagination defaults to page 1 and 25 rows, with a maximum page size of 100. Invalid filters/pagination return HTTP 400. Customer access returns HTTP 403. Missing warehouse/inventory/product records return HTTP 404 where applicable.

## Frontend routes and integration

- Register: `/app/warehouses`
- Detail: `/app/warehouses/:id`
- Navigation: Network Operations → Warehouses & Inventory
- Page 05 Hub Overview and Page 06 Hub Details include a shortcut into the corresponding warehouse inventory view.
- Shipment rows link to the existing Page 07 shipment detail panel.
- Product SKU links open the product's warehouse-level inventory where the products table supports the identifier.
- Browser history is supported for warehouse register/detail navigation.

The register includes database-backed KPI cards, Chart.js stock-status and warehouse inventory-record charts, search, active-state/location/disruption filters, sorting, pagination, refresh and CSV export. Warehouse detail includes identity, operational summary and tabs for inventory, shipments, disruptions, affected orders, recovery and audit activity. Inventory rows can open record detail or the cross-warehouse product inventory view.

## Data provenance and limitations

The workbook/demo seed records retain `data_origin` and source identifiers. Synthetic data remains labelled; it is not presented as verified live stock or live tracking. The base schema does not always create a `products` table until expanded dataset import; in that case inventory SKU/item data remain usable but product lookup is explicitly unavailable. No stock movement history, transfer records, replenishment confirmations, capacity assumptions, supplier purchase orders or live GPS/ETA data are created. Warehouse utilization/capacity fields are displayed only where stored. Unassigned disruptions remain unassigned.
