## 2. Preserved functionality

- Node.js native HTTP server, SQLite (`node:sqlite`), vanilla HTML/CSS/JavaScript and Chart.js.
- Exactly two authentication roles: `HUB_INCHARGE` and `CUSTOMER`.
- Five primary navigation destinations.
- Existing authentication, shipment, supplier, warehouse, inventory and order modules.
- Existing impact and deterministic risk engines.
- Existing disruption monitoring and read-only scenario simulation.
- Customer Portal and SQL-enforced customer order isolation.
- Existing import and carrier event services, extended additively.

## 3. Recovery recommendation workbench

- Added a recommendation workbench inside the existing Recovery Management page. No top-level navigation item was added.
- A Hub In-Charge selects a disruption, reviews its linked shipment, hub, affected orders, SKUs and inventory balances, then requests recommendations.
- Recommendations are generated by deterministic rules from verified inventory and order relationships.
- The current dataset does not contain supplier-to-SKU capability, supplier open capacity, carrier capacity, route feasibility, customer split-shipment acceptance, contractual penalty policy or transport pricing/ETA. Those options are not fabricated or shown as feasible.
- Inter-warehouse transfer options are labelled **Constrained** until a human verifies transport corridor, capacity, cost and ETA. Source available quantity and reorder point are checked again at execution.
- Unverified cost, delivery-time and risk-reduction estimates remain unavailable. Options are ranked only by recorded inventory coverage, not an invented score.
- Optional AI narrative uses the existing server-side `LLM_PROVIDER` / `LLM_API_KEY` integration. It explains supplied evidence only. Without a configured key, deterministic explanations remain available. AI never sets feasibility, risk scores, approval or execution state.

## 4. Recovery plan management

- A selected recommendation can create a persisted draft plan and action records.
- Plan fields include plan code, linked disruption, strategy, SKU, quantity, source/destination warehouses where applicable, description/rationale, creator, version, cost-estimate verification, status and timestamps.
- Permitted plan edits increment the version. Editing an approved plan invalidates its approval and returns it to Draft. Editing a rejected plan also returns it to Draft.
- Submission creates or reopens an approval request. Plans cannot be executed while Draft, Pending Approval, Rejected or Changes Requested.
- Recovery plan detail includes linked shipment/order impact, inventory snapshot, approval history and stock movement history.

## 5. Approval workflow

- Approval queue and decision history are displayed in Recovery Management.
- Supported decisions: Approve, Reject and Request Changes.
- Rejection and change requests require comments.
- A requester cannot approve their own plan. The backend verifies both the plan creator and approval requester against the acting user.
- Approval transitions run inside SQLite `BEGIN IMMEDIATE` transactions and use a pending-state compare-and-set to prevent duplicate decisions.
- If there is no independent active Hub In-Charge account, the plan remains pending. No synthetic or same-account approval is created.
- A helper script is included to create an additional Hub In-Charge account for a demonstration or deployment administrator. It reads credentials from environment variables and never prints the password.

## 6. Human-confirmed simulated execution

- The execution confirmation displays plan/disruption, linked shipment, affected orders, inventory availability/reorder threshold, quantity, known/unknown cost and customer accounts affected.
- The backend rechecks session/role, plan state, approved decision, independent approver identity, approved plan version, idempotency key, linked disruption and current inventory.
- A stock transfer checks available source stock and protects the source reorder point. It checks both warehouses are active and different.
- A valid simulated transfer updates source/destination inventory inside one transaction and writes a `stock_movements` record with `data_origin='simulated'`.
- Recovery actions and the recovery plan are marked executed in simulation mode. The execution audit record and result JSON are persisted.
- Customer orders and disruption status are deliberately not changed by the simulated transfer because physical receipt and fulfilment have not been verified.
- Duplicate execution, insufficient inventory, stale plan version, missing approval and missing human confirmation are rejected.
- No real carrier booking, purchase order, payment or physical delivery is performed.

## 7. Customer Portal and communications

- Customer order access continues to be scoped by the authenticated session's `customer_id` in SQL.
- The order detail response exposes only that customer's linked disruptions, approved/executed recovery plan summary, shipments and notifications.
- Draft and pending recovery plans are not exposed to customers.
- Manual customer updates require: verified affected-order link, a specifically selected recovery plan linked to the same disruption in Approved or Executed state, and explicit customer-disclosure confirmation.
- Simulated execution sends a customer notification only to active customer accounts linked to the affected orders. The message explicitly says the recovery action is simulated and does not assert physical shipment movement or delivery.
- Notification rows retain order, disruption and recovery-plan references. Customer notification reads remain scoped to the logged-in customer user.

## 8. Import enhancements

- CSV/JSON preview and explicit commit are retained.
- Supported entities: suppliers, warehouses, shipments and inventory.
- Suppliers and warehouses are insert-only. Existing codes are rejected rather than overwritten.
- Shipment and inventory duplicates are rejected by default. Updating matching records requires an explicit opt-in checkbox, revalidation and a second confirmation at commit.
- Validation covers required fields, data types, dates, status values, duplicate rows and relevant foreign-key references.
- Import processing remains transactional and audited. Maximum payload size remains enforced by the backend.
- Products, shipment items as independent import files, customer orders/order items and carrier events as bulk imports are not implemented because their complete safe import contracts and relationship semantics are not defined by the existing importer. Shipment import continues to support its existing single optional SKU/item fields. These are documented limitations, not fake import options.

## 9. Webhook reliability

- Simulated event IDs are caller-supplied or generated and are unique in SQLite.
- Duplicate IDs return an idempotent already-processed response and do not reapply the event.
- Supported event families include dispatch, delay, vehicle accident, weather, arrival, delivery, customs hold, port congestion and status updates.
- Invalid payloads, unsupported event types, invalid timestamps, unknown shipment references and stale/conflicting events are rejected and recorded as Failed where an event ID is available.
- Event timestamps are validated; future timestamps beyond the allowed clock tolerance and timestamps older than a previously processed event for the same shipment are rejected.
- Webhook history displays received time, event timestamp, ID, type, processing status and error/reason detail. Audit events are recorded.
- The simulator is not a live carrier integration.

## 10. Administration

- System status endpoint returns runtime, SQLite connectivity, configuration status and table counts.
- Account view exposes username/name, role, active state and last login only. Password hashes, API keys and secrets are never returned.
- Integration status clearly distinguishes configured AI from deterministic fallback and carrier simulator from a live carrier API.
- Import history is derived from import audit events. Webhook processing history is read from the webhook event table. Existing audit history remains available.

## 11. Additive database changes

- Added `stock_movements` with a foreign key to recovery plans and warehouses, positive quantity constraint, unique movement code, actor, timestamp and simulated provenance.
- Added `recovery_plans.cost_estimate_verified` to distinguish a human-entered/verified estimate from an unavailable estimate represented internally as zero for schema compatibility.
- Added `notifications.recovery_plan_id` to preserve the plan reference for customer communication.
- Added `webhook_events.error_details` for failed event diagnostics.
- Existing SQLite schema is not replaced. New columns use the repository's additive `ensureColumn` migration helper.

## 12. API additions / extensions

- `GET /api/v1/admin/system-status`
- `GET /api/v1/webhooks/history`
- `GET /api/v1/imports/history`
- `GET /api/v1/disruptions/:id/impact` now includes approved/executed recovery plan summaries.
- `GET /api/v1/recovery-plans/:id` now includes linked impact, current inventory snapshot, approval history and stock movements.
- `POST /api/v1/customer-updates` now requires a selected linked approved/executed recovery plan.
- `POST /api/v1/webhooks/simulate` now accepts stable event IDs and event timestamps and supports additional event types.
- Existing `/api/v1/recovery-plans`, `/from-recommendation`, `/submit-approval`, `/decision` and `/execute` APIs are reused.

## 13. Test results

Executed in the supplied environment after the final changes:

- `npm run check` – passed; all JavaScript files syntax-checked.
- `npm test` – passed; authentication, five primary pages, existing operational modules, disruption intelligence, deterministic risk, simulation immutability, recovery recommendation/approval/execution, insufficient-stock rejection, duplicate execution, customer notification, import safety, webhook idempotency and customer isolation assertions.
- `npm run test:dataset` – passed; 17 sheets × 350 synthetic records, relationships and idempotent import checks.

Browser visual automation was not run because Playwright/Puppeteer are not installed. The tests verify route access, JavaScript syntax, DOM anchors, backend integration and SQLite state, not pixel-perfect browser rendering.

## 14. Known limitations

- Recovery execution is a controlled database simulation. It does not represent physical stock transfer, dispatch, carrier booking, payment, purchase order or delivery confirmation.
- Only inventory-backed transfer recommendations are available where verified data supports them. Supplier alternatives, replacement products, refunds/compensation, order splitting and alternative transport are withheld until required operational facts and business rules exist.
- AI narrative is optional and depends on a configured provider/key. Deterministic recommendations and feasibility remain authoritative.
- Hub In-Charge is the maker and Recovery Manager is the independent checker. Use the dedicated recovery@disruptioniq.local demo account to approve, reject or request changes to submitted plans.
- Product, shipment-item, customer-order/order-item and carrier-event bulk imports remain unsupported as independent import entities.
- Live carrier integration, GPS, live external disruption feeds and route optimisation are not configured.
- Browser visual automation was not run.

## 13. Browser-safe local server ports

- Default local development port is now `3000`, which is accessible in Chromium-based browsers such as Microsoft Edge and Google Chrome.
- The server automatically skips browser-restricted ports, including SIP ports `5060` and `5061`, both when normalizing an explicitly configured `PORT` and when scanning for an available port.
- Startup output always prints the exact login URL to open. A regression test covers restricted-port normalization and fallback selection.
- Verified by starting the server with `PORT=5060 PORT_FALLBACK=false`; it correctly selected and printed `http://127.0.0.1:5062/login`.
